# Сборка ДЗ по подтверждённому предложению агента

Учитель подтверждает тему ДЗ на странице `/teacher/roadmaps/[id]/proposals/[proposalId]`
(кнопка «Подтвердить» переводит `homework_proposals.status` в `confirmed` —
см. `app/api/proposals/[id]/route.ts`). Дальше сборку теста делает не сервер
сам, а этот скилл: широкий SQL-фильтр отбирает МНОГО кандидатов по теме и
источникам, а финальный отбор — по смыслу текста каждого задания — делает
Claude Code, вручную запущенный учителем.

## Почему не автоматический build.ts

`lib/homework-agent/pick-problems.ts` для книжного источника (`book_problems`)
не умеет фильтровать по теме — `book_problems.section_id` не связан с
`library_topics`. Первый живой прогон (2026-09-16, программа «Броско
9-ОГЭ-М», тема «Функции») собрал ДЗ из комбинаторики, статистики, прогрессий
— книга отдавала задачи `ORDER BY used_count` по всей книге. Библиотечные
источники (`library_topic`/`library_exam`) фильтруются по теме корректно
(через `topic_id`/`canonical_topic_id`), но пользователь решил в любом
случае прогонять состав через смысловую проверку ИИ — SQL-фильтр по теме
даёт «предположительно относится», не «точно относится» (кодификатор
местами широкий, номер книги/раздела не гарантирует однородность условий).

`lib/homework-agent/build.ts` как модуль не удалён — он остаётся образцом
того, что нужно воспроизвести SQL-инсертами (структура test_tasks/
task_answer_keys/assignments, composite-разбор ответа), но сам он больше не
вызывается ни из PATCH `/api/proposals/[id]`, ни из cron — этот скилл его
заменяет как единственный путь сборки.

## Когда использовать

Пользователь просит «собери ДЗ для программы X», «запусти агента для
Y», «собери подтверждённое предложение» — без явного указания книги/темы
(если он называет книгу и тему прямо — это `.claude/skills/homework-from-books`,
не этот скилл).

## Вход, который нужно получить от пользователя (или уточнить)

- **Какая программа / какое предложение.** Если пользователь не назвал
  `proposalId` — найти по названию программы среди `status='confirmed'`
  (шаг 1). Несколько подтверждённых предложений подряд для разных программ —
  собрать все за один заход, если пользователь не просил конкретную.
- **Публиковать сразу или оставить черновиком** — по умолчанию черновик
  (`homework_proposals.publish_immediately`, если не выставлен явно — не
  публиковать без явной просьбы, тот же принцип, что в build.ts и в
  `homework-from-books`).

## Пошагово

Все SQL — через `scripts/supabase-query.mjs`, не `mcp__supabase__execute_sql`
(экономит вызов MCP-инструмента, стабильно доступен из скиллов). SQL — не
через `echo`/`printf` в Bash (шелл теряет экранирование в строках с
кавычками/LaTeX) — `Write` payload `{"sql": "..."}` в
`.claude/tmp/query-<имя>.json`, затем `node scripts/supabase-query.mjs <
файл`, затем `rm` файл.

### 1. Найти подтверждённое предложение и его контекст

```sql
select p.id as proposal_id, p.roadmap_id, p.rule_id, p.organization_id, p.teacher_id,
       p.roadmap_topic_id, p.proposed_title, p.final_title, p.publish_immediately,
       rt.library_topic_id, r.title as roadmap_title,
       lt.name as topic_name, lt.fipicod
from homework_proposals p
join roadmaps r on r.id = p.roadmap_id
left join roadmap_topics rt on rt.id = p.roadmap_topic_id
left join library_topics lt on lt.id = rt.library_topic_id
where p.status = 'confirmed'
order by p.confirmed_at desc;
```

Колонка называется `fipicod` (без подчёркивания) — `library_topics` не
содержит `fipi_code`, эта опечатка встречалась в более ранней версии файла
и ломала запрос при живом прогоне.

Если `library_topic_id` пуст — предложению не проставлена тема кодификатора,
собрать нельзя (та же проверка, что в `build.ts`), сообщить пользователю и
остановиться для этого предложения (не для всех остальных найденных).

### 1.5. Раскрыть тему в подтемы, если это родительский код

Кодификатор ОГЭ/ЕГЭ — двухуровневая иерархия (`library_topics.parent_id`):
код `5` «Функции» — родитель, `5.1`–`5.4` — конкретные подтемы, у каждой
свой пул задач в библиотеке. Цель точечного ДЗ — искать по **самому узкому
уровню, который есть** — если diagnose/roadmap_topics дал родителя, взять
кандидатов сразу по всем его детям (объединив), а не только по родителю
буквально (у родительских кодов `library_problems.topic_id` почти всегда
пусто — см. проверку ниже, широкая тема сама по себе не находит кандидатов).

```sql
select id, fipicod, name, parent_id
from library_topics
where id = '<library_topic_id>' or parent_id = '<library_topic_id>';
```

- Если вернулась только сама строка (`parent_id` не совпал ни с чем, у темы
  нет детей) — это уже лист, дальше используем один `<library_topic_id>` как
  раньше.
- Если вернулось несколько строк с `parent_id = <library_topic_id>` — это
  родитель, дальше по шагу 3 подставляем **весь список id детей**
  (`topic_id in (...)`), не сам родительский id.
- `roadmap_topics.library_topic_id` в проверенных программах пока привязан
  к листу напрямую (см. project_homework_agent) — этот шаг в основном
  подстраховка на случай, если diagnose.ts или ручная правка учителя когда-
  нибудь отдаст родительский код; тогда без этого шага пул кандидатов на
  шаге 3 будет пустым или почти пустым.

### 2. Прочитать правило и его источники

```sql
select ars.source_kind, ars.book_id, ars.library_topic_id, ars.exam_type,
       ars.subject, ars.weight,
       r.task_count, r.mistakes_pct, r.difficulty, r.allow_images, r.require_answer
from roadmap_agent_rule_sources ars
join roadmap_agent_rules r on r.id = ars.rule_id
where ars.rule_id = '<rule_id>';
```

`task_count` — сколько заданий нужно в итоге. Дальше в шаге 3 нужно взять
кандидатов **с большим запасом** (минимум ×3-4 от `task_count`, всё что
формально проходит лёгкий фильтр — не обрезать по количеству на этом шаге),
чтобы после смыслового отсева осталось из чего выбирать.

### 3. Собрать широкий пул кандидатов — лёгкий фильтр, без обрезания по теме для книг

Для источников `library_topic`/`library_exam` (тема фильтруется по
`topic_id`/`canonical_topic_id` — надёжно):

```sql
select lp.id, lp.prompt_text, lp.has_answer, lp.correct_answer, lp.default_max_score,
       lp.used_count,
       exists (
         select 1 from library_problem_media m
         where m.library_problem_id = lp.id and m.placement <> 'solution'
       ) as has_condition_images
from library_problems lp
where (lp.topic_id in (<id темы + все её дети из шага 1.5>)
    or lp.canonical_topic_id in (<тот же список>))
  and lp.is_active = true
  and (<require_answer=false> or lp.has_answer = true)
order by lp.used_count asc
limit <task_count * 4>;
```

Колонка называется `library_problem_id` (не `problem_id`) — та же опечатка,
что и `fipi_code` выше, встречалась в более ранней версии файла.

Если тема — родитель с несколькими детьми (шаг 1.5), полезно на этом же
запросе добавить `lt.fipicod as matched_subtopic` (join к `library_topics`
через `topic_id`/`canonical_topic_id`) — при отборе на шаге 4 это помогает
равномерно распределить состав по подтемам, а не набрать все 8 заданий из
одной случайно преобладающей подтемы (5.1 «график функции» в библиотеке
почти всегда многочисленнее 5.4 «описание зависимостей»).

Для источника `book` — **это ключевое отличие от старого pick-problems.ts**:
не полагаться на `section_id` (не связан с кодификатором), собрать
кандидатов по книге широко и положиться на текстовый анализ в шаге 4:

```sql
select bp.id, bp.task_number, bp.prompt_md, bp.correct_answer, bp.answer_source,
       bp.has_images, bp.difficulty, bp.used_count
from book_problems bp
where bp.book_id = '<book_id>'
  and bp.is_active = true
  and (<require_answer=false> or (bp.answer_source <> 'none' and bp.correct_answer is not null))
  and (<allow_images=true> or bp.has_images = false)
order by bp.used_count asc
limit <task_count * 6>;
```

Больший запас для книги (×6, не ×4) — у книжного источника ожидаемо низкая
доля кандидатов пройдёт смысловую проверку (раздел книги шире темы
кодификатора), у библиотечного — почти все, раз тема уже совпала точно.

Исключить уже недавно назначенные тому же учителю тем же ученикам —
`assigned_problems` (052), окно 60 дней (то же, что `dedupWindowDays` в
старом `pick-problems.ts`), фильтр обязательно по `teacher_id`:

```sql
select problem_id from assigned_problems
where teacher_id = '<teacher_id>' and assigned_at > now() - interval '60 days';
```
Вычесть эти id из обоих пулов перед шагом 4 (не включать их в текст на
чтение — если задание уже недавно задавалось, оно не кандидат вообще,
независимо от смыслового соответствия).

### 3.5. Найти реальные ошибки группы и сгруппировать их по смыслу

`exam_task_topic_map` (см. project_homework_agent, известное ограничение)
определяет тему ошибки только на уровне родителя («Функции» вообще, не
«5.1» или «5.3») — статистика по номеру задания размыта, разные варианты
ОГЭ ротируют темы под одним и тем же номером. Точность на уровне подтемы
даёт не карта, а прямое чтение текста реальных ошибок этой конкретной
группы — их немного (десятки, не тысячи), это разовое чтение окупается
точностью состава.

```sql
select t.kind, tt.id as task_id, tt.task_number, tt.prompt_text, tt.has_images,
       count(distinct ata.attempt_id) as students_wrong
from attempt_task_answers ata
join attempts at on at.id = ata.attempt_id
join test_tasks tt on tt.id = ata.task_id
join test_versions tv on tv.id = tt.test_version_id
join tests t on t.id = tv.test_id
where ata.is_correct = false
  and at.status in ('submitted','checked')
  and at.student_id in (<studentIds программы>)
  and at.submitted_at > now() - interval '<mistakes_lookback_days> days'
order by students_wrong desc;
```

Запрос сознательно **не фильтрует `t.kind`** — берёт ошибки и из пробных/
контрольных (`kind='test'`), и из прошлых ДЗ (`kind='homework'`) вместе.
В живом прогоне 2026-09-17 у программы «Броско 9-ОГЭ-М» из 91 ошибки почти
все (83) оказались из `test`, лишь 8 из `homework` — при таком перекосе
разделение пока не даёт дополнительной точности, `homework` слишком мало,
чтобы формировать отдельный сигнал. **Когда накопится достаточно ошибок
именно в ДЗ** (не разово, а систематически — по программе или по всей
организации) — стоит считать `p` раздельно по `kind` и решать, весить ли
их одинаково (аргумент за общий пул: тест — более честный сигнал пробела,
ученик пишет самостоятельно без права переспросить; аргумент за раздельный
счёт: ошибка в старом ДЗ, которое само было реакцией на диагноз, не должна
задавать направление для нового ДЗ той же циклично). Не вводить это
разделение заранее «на всякий случай» — при текущем объёме данных сложность
не оправдана.

Дальше — не подставлять эти строки напрямую в диагноз, а обработать:

1. **Прочитать `prompt_text` (условие, без ответа ученика — ответы не
   расписаны в тесте, только текст задачи и `has_images`/наличие таблицы,
   графика и т.п. как метаданные) каждой ошибочной задачи.**
2. **Сгруппировать по смыслу, не по `task_number`.** Одна и та же проблема
   («установите соответствие график↔формула») может встречаться под разными
   номерами в разных вариантах — это один кластер, а не два. Пример из
   живых данных программы «Броско 9-ОГЭ-М»: task_number 5 («графики вида…
   указать...») и task_number 11 («установите соответствие график↔формула»)
   — одна и та же проверяемая проблема, кластер один.
3. **Посчитать долю группы `p` на кластер — по уникальным ученикам**, не
   суммой по заданиям (ученик, ошибившийся в обоих заданиях кластера,
   считается один раз, не два): `p = |ученики с хотя бы одной ошибкой из
   кластера| / |всего учеников программы|`.

### 4. Прочитать текст каждого кандидата, сравнить с реальными ошибками, отобрать состав

Это шаг, ради которого существует весь скилл — **не пропускать, не
подставлять первые N по порядку**. Порядок отбора — от конкретного к общему:
сначала закрываем реальные ошибки группы похожими задачами, остаток —
на соседние подтемы той же родительской темы (текущая тема программы,
не рассмотренная в ошибках).

**Для каждого кластера ошибок (шаг 3.5), по убыванию `p`:**

- Взять условие эталонной задачи кластера (текст + `has_images`) и сравнить
  с каждым кандидатом из пула (шаг 3) в два приёма: сначала структурное
  совпадение (тот же тип задачи — «найти по графику», «установить
  соответствие», та же форма условия), затем смысловое (тот же навык при
  другой формулировке). Отбраковать кандидатов, структурно похожих, но по
  факту про другой навык (пример живого инцидента: тема «Функции», но
  задача о комбинаторике/статистике без функциональной записи — не
  подходит, даже если формально из того же раздела книги).
- **Сколько задач дать на кластер — оценить по `p`, не по фиксированной
  формуле с порогами.** Ориентир (плавная кривая, без резких скачков и
  без единственно верного числа — каждая ситуация уникальна):
  - `p < 10%` → 1 задача, не пропорция, минимум достаточный для точечного
    напоминания;
  - далее доля состава растёт с `p` нелинейно, ускоряясь к верхней границе
    — ориентировочно около трети состава при `p≈50%`, и до ~75% состава
    при `p`, близком к 100% (почти вся группа не справилась — это не один
    пробел среди прочих, а тема, которую нужно почти полностью повторить);
  - между этими точками не должно быть ступеньки/разрыва — если несколько
    кластеров конкурируют за один и тот же `task_count`, распределять
    пропорционально их `p`, соблюдая суммарно этот ориентир, а не подставлять
    в формулу механически.
- Кандидаты, не подошедшие ни одному кластеру ошибок (или если ошибок
  вообще не нашлось на шаге 3.5 — предложение основано только на текущей
  теме программы, без диагноза по ошибкам) — заполняют остаток `task_count`
  по подтемам родительской темы (шаг 1.5), с прежним принципом
  диверсификации: минимум 1 задание на подтему, у которой есть хоть один
  смыслово подходящий кандидат, не больше 2 заданий одинаковой формулировки
  подряд (банк ОГЭ склеивает похожие задания в кластеры по частоте — в
  живом прогоне 2026-09-16 из 40 кандидатов подтемы 5.1 больше 30 были
  одним и тем же паттерном формулировки).
- Если после отсева наскребается меньше `task_count * 0.5` — не собирать тест
  вслепую с нехваткой (тот же порог `MIN_ACCEPTABLE_RATIO`, что в старом
  `pick-problems.ts`); сообщить пользователю, что источников по теме
  недостаточно, предложить расширить источники правила или снизить
  `task_count` — не тянуть посторонние задачи ради количества.

### 5. Определить `teacher_id`/`organization_id`

Уже есть из шага 1 (`p.teacher_id`, `p.organization_id`) — предложение
принадлежит конкретному учителю, спрашивать не нужно (в отличие от
`homework-from-books`, где владелец не всегда очевиден).

### 6. Создать черновик ДЗ и перенести отобранные задания

```sql
insert into tests (organization_id, title, kind, status, created_by)
values ('<organization_id>', '<final_title или proposed_title>', 'homework', 'draft', '<teacher_id>')
returning id;

insert into test_versions (test_id, version_number, status)
values ('<test_id>', 1, 'draft')
returning id;
```

Для каждого отобранного задания, по порядку (`task_number`/`sort_order` = позиция с 1):

- Источник `book` — тот же процесс вставки, что в `.claude/skills/
  homework-from-books/SKILL.md` шаг 5 (composite-разбор через
  `scripts/classify-answer.mjs`, `max_score` = число пунктов а)/б)/…,
  инкремент `book_problems.used_count`). Не изобретать заново — скопировать
  ту же процедуру буквально.
- Источник `library_topic`/`library_exam` — аналогично, но эталон
  (`correct_answer`) у `library_problems` — голая строка, не `{text: ...}`
  как у книг; медиа условия (`library_problem_media` с `placement <>
  'solution'`) при копировании в тест — физически копировать storage-объект
  из бакета `library-media` в `task-media` (`admin.storage.from('library-media')
  .copy(...)` в терминах TS-эквивалента `addLibraryProblemToVersion` из
  `lib/tests/add-problem-to-version.ts` — прочитать этот файл перед вставкой
  библиотечных заданий, если такие есть в отборе, воспроизвести SQL-эквивалент
  того же порядка операций: task → task_answer_keys → task_solutions → media
  → used_count).

### 6.5. Проверка качества каждого отобранного задания перед вставкой

Смысловая проверка на шаге 4 отвечает только «подходит ли тема», не «можно
ли автоматически проверять ответ». Перед вставкой каждого отобранного
задания — обязательная трёхветвевая проверка (найдена на практике: задача
9.7 из задачника Мордковича, `book_problems.id='34afb070-...'`, формально
имела `answer_source='book_answers'`/`correct_answer` не null — прошла бы
без этой проверки, но эталон был битым OCR-обрывком «6) $10 u; B 4\frac{1}
{8}...», непригодным для автопроверки):

1. **Ответ есть и читаемый.** Разобрать `correct_answer` глазами: цельные
   числа/выражения по каждому пункту а)/б)/в)/г), без смешения кириллицы/
   латиницы, без обрывков формул, без служебных меток соседних номеров
   (`book_problems`, где ответы книги распознаны OCR блоком, иногда цепляют
   хвост следующей задачи — как в примере выше «...г) 0,3 мин. 8.35. а)...»).
   Если чисто — вставлять как есть.
2. **Ответа нет** (`has_answer=false`/`correct_answer is null`/
   `answer_source='none'`) **или ответ битый** (не прошёл проверку в п.1) —
   решить самостоятельно тем же приёмом, что шаг 6 в `homework-from-books`
   (sympy для точных вычислений, `classify-answer.mjs` для формата и
   composite-разбора). Для `book_problems` — записать исправленный
   `correct_answer` обратно с `answer_source='manual'` (не только в
   `task_answer_keys` собранного теста) — тогда следующая сборка ДЗ из этого
   же раздела книги получит уже чистый ответ, не будет чинить его повторно.
   Для `library_problems` — не перезаписывать общую библиотеку (это чужой,
   общий для всех организаций источник, не то же самое, что решать книжные
   задания для многоразового использования конкретно этой книги) — исправленный
   ответ живёт только в `task_answer_keys` этого теста.
3. **Условие опирается на медиа** (`has_images=true`, наличие таблицы/
   графика/рисунка в тексте или `library_problem_media`/`book_problems`
   с непустым набором изображений) — прочитать не только текст, но и
   убедиться, что медиа реально скопируется на шаге 6 (storage-объект
   существует, `placement <> 'solution'`), а не только текстовую часть
   условия. Задание, где ответ или ход решения зависит от таблицы/графика
   («на рисунке изображены графики…», «в таблице приведены нормативы…») —
   без этой проверки рискует попасть в тест с условием, ссылающимся на
   несуществующую или непрокопированную картинку. Если медиа физически не
   скопировалось (ошибка `storage.copy`, шаг 6) — не оставлять задание в
   составе молча, заменить на другого кандидата или явно предупредить
   пользователя в итоговом отчёте.

### 7. Обновить homework_proposals и отчитаться

```sql
update homework_proposals
set status = 'built', test_id = '<test_id>', updated_at = now()
where id = '<proposal_id>';
```

Если по ходу решили опубликовать (`publish_immediately=true` или явная
просьба пользователя) — публикация версии теста (см. `lib/tests/publish.ts`
для инвариантов: все `test_tasks.review_status='approved'`, у каждого
задания есть `task_answer_keys`) и создание `assignments` с
`roadmap_topic_id = <roadmap_topic_id из шага 1>`, `kind='homework'`,
`group_id` программы — SQL-эквивалент того, что делает `doBuild` в
`lib/homework-agent/build.ts` после `pickProblems` (прочитать этот файл,
строки после `publishResult` — тот же порядок insert, тот же набор колонок).
Если публикуем — при ошибке публикации откатывать `homework_proposals` в
`failed` с `build_error`, не оставлять «built» без реального теста.

Доложить пользователю на русском: тема, `test_id`, сколько кандидатов
рассмотрено против скольких отобрано (по источникам — книга/библиотека),
сколько отбраковано по смыслу и почему коротко (1 фраза на паттерн отсева,
не на каждое задание), сколько с готовым ответом «из источника» против
«решено самостоятельно». Если состав опирался на реальные ошибки группы
(шаг 3.5) — отдельно назвать кластеры и их долю `p` (например «график↔
формула — ошиблось 43% группы, дано 3 похожих задания»; «остальные 5 —
по соседним подтемам без диагноза по ошибкам») — учителю важно видеть, что
именно из состава реакция на факт, а не общее покрытие темы.

## Ограничения

- Не публикует по умолчанию (`status` остаётся `draft`) — как и
  `homework-from-books`, публикация — явный шаг.
- Не трогает `homework_proposals` со статусом, отличным от `confirmed` —
  если пользователь просит пересобрать уже `built`/`failed` предложение,
  сначала явно перевести его обратно (обнулить `test_id`, удалить старый
  черновик тем же способом, что при откате инцидента 2026-09-16 — удалить
  `test_tasks`/`task_answer_keys`/`test_versions`/`tests`, обнулить
  `tests.current_published_version_id` перед удалением версий).
- Не меняет `roadmap_agent_rules`/`roadmap_agent_rule_sources` — если
  источник в принципе даёт мало релевантных кандидатов (шаг 4, порог 50%),
  это сигнал пользователю поправить источники правила, не повод скиллу
  тихо ослаблять фильтры сверх того, что уже заложено (require_answer/
  allow_images — можно ослаблять по тому же принципу фолбэков, что был в
  `pick-problems.ts`, difficulty/тему — нет).
