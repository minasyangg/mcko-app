# Ревьюер ответов книги

Заполняет `book_problems.correct_answer` для заданий с `answer_source='none'`,
решая их напрямую (собственным рассуждением в этой сессии — по подписке
Claude Code, без отдельного Anthropic API ключа и без DeepSeek). Точечная
онлайн-генерация (кнопка «Ответ ИИ» в UI, DeepSeek) и этот скил — два разных,
независимых пути к одному результату (`answer_source='ai'`); скил замещает
только массовую офлайн-обработку целой книги.

## Когда использовать

Пользователь просит «прогони книгу X», «сгенерируй ответы для [учебника]»,
«добавь ответы там где их нет» — для книги, уже лежащей в `books`/
`book_problems` (импортированной через `scripts/book-import.mjs`).

## Пошагово

### 1. Найти книгу

Если передан явный `book_id` (uuid) — использовать как есть. Если передано
название/предмет/класс, найти через `scripts/supabase-query.mjs` (не Supabase
MCP — скрипт подключается к Postgres напрямую). SQL — **не через `echo`/
`printf` в Bash** (шелл теряет/портит экранирование в строках с кавычками —
подтверждено эмпирически, см. `.claude/memory/progress.md`, раздел «Найден
баг конвейера»): `Write` payload в `.claude/tmp/query-<произвольное имя>.json`
(`{"sql": "..."}`), затем `node scripts/supabase-query.mjs < файл` через Bash,
затем `rm` файл — тот же приём, что и для `classify-answer.mjs` (шаг 5).

```sql
select id, title, subject, grade, level
from books
where title ilike '%<кусок названия>%'
order by created_at desc;
```

Несколько совпадений — показать список, уточнить у пользователя. Ничего не
найдено — сказать явно, не выдумывать книгу.

### 2. Собрать задания без ответа

Тем же способом (`Write` → `node scripts/supabase-query.mjs < файл` → `rm`):

```sql
select id, task_number, task_number_sort, prompt_md, has_images, options
from book_problems
where book_id = '<book_id>'
  and answer_source = 'none'
  and correct_answer is null
  and is_active = true
order by task_number_sort nulls last;
```

Возвращает `{"results":[{"command":"SELECT","rowCount":N,"rows":[...]}]}` —
использовать `results[0].rows`. Разделить результат: `has_images = true` →
сразу в «пропущено (картинки)», дальше не трогать (текстовый ревью их не
решает — как и online-путь). Дать пользователю сводку: всего без ответа /
пропущено картинок / в работу.

Если «в работу» пусто — сообщить и остановиться.

### 3. Прогреться на выборке (первые ~10)

Взять первые ~10 заданий из очереди и решить их через маршрутизацию на
решателей (см. шаг 5) — так же, как в шаге 4, просто одним небольшим
подсписком. Показать пользователю таблицу «№ → ответ → метод», спросить,
продолжать ли на всю книгу — так же, как раньше `--dry-run` в скрипте. Если
пользователь уже явно попросил «прогони всю книгу без остановки» — можно
пропустить этот чек-пойнт.

### 4. Обработать очередь батчами

Держать прогресс в TodoWrite (по одной задаче на батч ~20-30 заданий — книга
на 300+ заданий иначе не влезет в разумный отчёт и легко потерять место).

Батч (до ~25 заданий) как единица работы — прежний, но исполняется НЕ отдельным субагентом на
каждый батч. **Волну батчей делить на 2 равные последовательности** (например батчи 1,3,5...
воркеру А, батчи 2,4,6... воркеру Б — любое равное разбиение) и запускать ровно **2 параллельных
вызова Agent** (`subagent_type: task-orchestrator`, не `general-purpose`), каждому передавая его
ПОЛНЫЙ список батчей (SQL-запросы/офсеты) одним промптом. Воркер обрабатывает свои батчи строго
последовательно внутри этого одного вызова — не создаёт под-субагента на каждый батч своего
списка (подробно — `.claude/agents/task-orchestrator.md`). На волну из N батчей — 2 вызова
Agent, не N.

**Критично для расхода токенов этой сессии**: весь рабочий цикл батча (SQL-запрос,
делегирование `task-solver-haiku`, классификация, запись в БД) должен оставаться внутри
контекста воркера-субагента — сюда, в эту сессию, попадает только финальная сводка воркера (по
строке на батч + суммарный итог его батчей), без единого промежуточного Write/Bash-вызова и без
текстов/ответов отдельных заданий. Для этого воркер обязан вызывать `task-solver-haiku`
синхронно (`run_in_background: false`) — если вызвать в фоне, ход воркера прерывается и ответ
решателя уходит в эту сессию вместо воркера, и тогда эту сессию вынуждает вручную пересылать его
обратно воркеру (проверено на практике — так контекст этой сессии уходил с 36% до 100% за 5
батчей). Подробности — раздел «Критично» в `.claude/agents/task-orchestrator.md`, не дублируются
здесь.

**Воркер сам не решает задания и не перепроверяет ответы решателя** — маршрутизирует их решателю,
классифицирует (`classify-answer.mjs`) и пишет в БД. От каждого воркера — только итоговая сводка
по его батчам (решено/пропущено-по-категориям/гонки на батч + сумма), без пересказа каждого
задания. После обоих воркеров — сложить их сводки в одну сводку по волне целиком.

### 5. Маршрутизация на решателя

Ниже — общее описание процедуры; точная механика вызовов (в т.ч. `run_in_background: false` для
решателя и Write-файлы вместо `echo`/`printf`) закреплена в `.claude/agents/task-orchestrator.md`
и обязательна к соблюдению именно в том виде — при расхождении с текстом ниже прав
`task-orchestrator.md`, не дублировать/не расходовать токены на сверку вручную.

1. Прочитать `prompt_md` каждого задания батча (может содержать LaTeX
   `$...$`/`$$...$$` — не мешает пониманию условия, решатель разбирает его
   сам).
2. Делегировать **весь батч одним списком** в `task-solver-haiku` —
   **единственный решатель конвейера, деления по сложности и эскалации
   нет.** Один вызов Agent (`subagent_type: task-solver-haiku` — буквально
   эта строка, не описательная ссылка на файл) на список, не на задание
   (см. `AGENTS.md` → «Оркестрация расчётов»). Передать решателю: `id`,
   `task_number`, `prompt_md`, `options` каждого задания. **Никогда не решай
   задания сама/сам в потоке оркестратора** — это работа решателя
   (`.claude/agents/task-solver-haiku.md`; там же — правила самого решения:
   LaTeX, формат ответа, точные вычисления через `sympy`/`exact_math.py`,
   когда пропускать).
3. Решатель возвращает по каждому заданию: решённый ответ либо пометку
   «пропустить». **Не пересчитывай и не перепроверяй его ответы
   самостоятельно — ни для валидации, ни для какой-либо другой цели.** Если
   вычисление было корректно передано в скрипт, результат точен по
   построению; повторное решение — трата токенов на уже сделанную работу, а
   не польза.
4. Для каждого решённого ответа — классифицировать метод проверки, не подбирать вручную и не
   писать для этого свой скрипт. **Не через `echo`/`printf` в Bash** — ручная сборка JSON с
   LaTeX-бэкслешами в shell-строке эмпирически портит экранирование незаметно (см.
   `.claude/memory/progress.md`, раздел «Найден баг конвейера»). Вместо этого: `Write` payload
   `{"promptMd":"<prompt_md>","answerText":"<решённый ответ>"}` в
   `.claude/tmp/classify-<id задания>.json`, затем Bash `node scripts/classify-answer.mjs <
   .claude/tmp/classify-<id задания>.json`, затем `rm` файл — тот же приём Write→Bash→rm, что и
   везде в этом скиле.

   Вернёт `{cleanedAnswer, gradingMethod, answerFormatHint, isComposite}` — использовать только
   `cleanedAnswer`/`gradingMethod`/`isComposite` для записи (шаг 6), не печатать сырой JSON в
   вывод. Это тот же код, что применяется к online-генерации и парсингу PDF — не дублировать
   логику вручную в уме.

### 6. Записать результат

`classify-answer.mjs` возвращает поле `isComposite`. В зависимости от него
формат записи в БД отличается:

**Простой ответ (`isComposite: false`):**
```sql
update book_problems
set correct_answer = jsonb_build_object('text', '<cleanedAnswer, экранировать кавычки>'),
    grading_method = '<gradingMethod>',
    answer_source = 'ai',
    updated_at = now()
where id = '<problem_id>'
  and answer_source = 'none';
```

**Составной ответ (`isComposite: true`):**
`correctAnswerJson` уже имеет нужную форму `{"parts": {"а": {"value": "...", "method": "..."}, ...}}` —
записывать его напрямую, без обёртки `{text: ...}`:
```sql
update book_problems
set correct_answer = '<correctAnswerJson как ::jsonb>',
    grading_method = 'normalized',
    answer_source = 'ai',
    updated_at = now()
where id = '<problem_id>'
  and answer_source = 'none';
```

Пример подстановки (PostgreSQL автоматически кастит строку в jsonb):
```sql
set correct_answer = '{"parts":{"а":{"value":"5/6","method":"numeric_tolerance"},"б":{"value":"18/7","method":"numeric_tolerance"}}}'::jsonb
```

Выполнять через `scripts/supabase-query.mjs`, тем же способом, что и в шагах
1-2: `Write` payload (`{"sql": "<UPDATE-запросы через ';'>"}`) в
`.claude/tmp/query-<имя>.json`, `node scripts/supabase-query.mjs < файл`,
`rm` файл. Ответ — `{"results":[{"command":"UPDATE","rowCount":N}, ...]}`,
один элемент массива на каждый `UPDATE`. Можно батчить несколько `UPDATE` в
одном вызове через `;` в одной строке `sql` — скрипт выполняет их по очереди
в одной транзакции. Проверить `rowCount` каждого — 0 означает гонку (кто-то
уже ответил), не ошибка, просто пропустить в отчёте.

### 7. Итоговый отчёт

По завершении (или после каждого батча, если книга большая и требует
нескольких сообщений/дней): решено / пропущено (картинки) / пропущено
(неуверенность) / гонки. Напомнить пользователю: **выборочно сверить 5-10
ответов с ответами в конце бумажной книги** перед тем как полагаться на них
для авто-проверки учеников — это ИИ-эталон, а не сверенный факт.

## Ограничения

- Не трогает `library_problems` (это только для `book_problems` — библиотека
  ФИПИ/sdamgia размечается по-другому и online-путём через
  `/api/library/problems/[id]/ai-answer`).
- Не трогает задания с картинками (`has_images=true`) — текстовый ревью их
  не видит; для них остаётся online-путь через UI (кнопка «Ответ ИИ» тоже их
  пропускает) либо ручной ввод учителем.
- Не создаёт `task_answer_keys` — это происходит позже, при добавлении
  задания в тест (`add-to-test`), которое уже само подхватывает
  `book_problems.correct_answer`, если он есть на момент добавления.
